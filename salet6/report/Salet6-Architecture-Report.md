# Salet6 System Architecture Report

## 1. Design goal & architecture

**Tales9** is a smart bar table: placing a coaster triggers a drink-specific animation and visual identity. **Salet6** lets a venue owner brand that experience in five steps—**Concept → Generate → Compare → Edit → Apply**—without a design team, without API keys in the browser, and without AI calls on the table during service.

The design goal is **fast, operator-safe venue branding** under Tales9 constraints: one PixiJS app, coaster response under 100ms, 60fps, and **offline operation** after apply. AI runs only during authoring; the table consumes a pre-validated `ThemePackage`.

```
Authoring (packages/salet6, :5173)  ──HTTP/WS──►  Bridge (packages/bridge, :8787)
  wireframe index.html + authoring-bridge.ts         Express · Provider mock|poe
                                                     compile · uploads · Poe API
         WS APPLY_THEME ◄──────────────────────────►  Runtime (display-app-stub, :5174)
                                                     PixiJS · Zod validate · ACK · reset
```

All layers share **`packages/shared`** (Zod schemas + WS message types). UX was first validated in a Poe Canvas prototype, then implemented in-repo; stakeholder feedback (Plans A/B/C, per-drink coasters) is recorded in `docs/Poe-Canvas-Salet6-Prototype-Interactions.md`.

## 2. Technical pipeline

| Step | Action |
|------|--------|
| 1 | Operator enters brand, preset, and 1–5 drinks in Salet6. |
| 2 | Bridge `POST /api/generate-plans` → three `DesignPlan` directions (A/B/C). |
| 3 | Operator selects a plan; bridge `POST /api/select-plan` → `DrinkProfile[]` + asset prompts. |
| 4 | Edit palette/motion/lighting; optional `POST /api/nl-edit`; per-drink `POST /api/generate-drink-character`; Apply page `POST /api/generate-coaster-animation`. |
| 5 | Bridge `POST /api/compile-runtime` → `ThemePackage` with Pixi coaster artifacts. |
| 6 | WebSocket `APPLY_THEME` → runtime validates, applies, ACKs; **resets table** on re-apply. |

Coaster code is generated by `claude-haiku-4.5`, dry-run validated on the bridge, transpiled with esbuild, and bundled into `runtimeArtifacts`. Mock/stub fallback runs when codegen fails. Remote drink images are cached under `/uploads` and proxied via `/api/asset-proxy` for CORS-safe Pixi loading.

## 3. Prompt engineering

Canonical prompts live in **`packages/shared/src/promptBuilders.ts`**; the bridge executes them in `poe.ts` and returns **`promptUsed`** to the Generate loader so operators see the exact prompt sent.

- **Role + schema-in-prompt** — each call assigns a role and specifies JSON shapes for `DesignPlan`, `ThemeConfig`, and `DrinkProfile` before Zod validation.
- **Context injection** — brand text, preset, drink menu, and selected theme JSON are embedded in every call (session augmentation, not vector retrieval).
- **Strict JSON channel** — fence stripping, parse, Zod validate; partial select-plan output is **merged** with plan preview when the LLM omits fields (e.g. `motion`).
- **Two-step drink character** — text metadata first, then a separate image prompt for the visual preview.
- **Reliability** — `PoeProvider` falls back to `MockProvider` on failure; the Poe Canvas prototype used a keyword NL parser; production `nl-edit` sends full `ThemeConfig` plus the operator instruction.

## 4. Function calling & RAG

**Function calling** is implemented as **typed HTTP endpoints + a swappable Provider interface** (`mock` | `poe`), validated by Zod at each boundary:

| Endpoint | Output |
|----------|--------|
| `/api/generate-plans` | `DesignPlan[]` |
| `/api/select-plan` | `DrinkProfile[]`, asset prompts |
| `/api/nl-edit` | `ThemeConfig` |
| `/api/generate-drink-character` | metadata + `imageUrl` |
| `/api/generate-coaster-animation` | Pixi source |
| `/api/compile-runtime` | `ThemePackage` |

**RAG:** no production vector database. We use session context in prompts, normative docs (`Salet6PRD.md`, Tales9 PRD, prototype interaction log), and Zod schemas as ground truth—reducing semantic drift without chunk retrieval.

## 5. Models & alignment with design goal

All models route through **Poe** (`api.poe.com/v1`); `POE_API_KEY` stays on the bridge only.

| Capability | Model |
|------------|-------|
| Plans, select-plan | `gemini-3.5-flash` (`POE_TEXT_MODEL`) |
| NL edit, coaster codegen | `claude-haiku-4.5` (`POE_EDIT_MODEL`, `POE_CODE_MODEL`) |
| Drink visual preview | `imagen-4-fast` or `Flux-Schnell-T` (`POE_IMAGE_MODEL`) |

Text and image calls are decoupled so metadata survives image failures.

| Design intent | Implementation |
|---------------|----------------|
| Three directions before commitment | `generate-plans` → Compare → `select-plan` |
| Per-drink coasters + drink photos | `DrinkProfile` + coaster codegen + Pixi stub |
| NL tweaks & operator trust | `nl-edit`; `promptUsed` in loader; grey “press Apply to Table” until WS apply |
| Safe, offline table runtime | Compile before apply; no Poe calls at runtime; stub resets on re-apply |

**MVP limits:** logo upload is persist-only; drink photo upload is mock; `display-app-stub` suffices for grading (Tales9 sibling repo optional).

Salet6 connects prompt engineering, structured LLM outputs, multimodal images, and tool-like HTTP orchestration—to a physical design goal: branded interactive bar tables, with a versioned `ThemePackage` as the handoff artifact.
